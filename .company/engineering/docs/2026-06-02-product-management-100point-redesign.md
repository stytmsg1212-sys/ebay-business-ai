出典: 2026-06-02 user 要望「いろんな軸の金額が点在してごちゃつき。シンプル + 高速 + サクサクな商品管理画面を Codex と100点で設計」。W212(損益分岐/washing修正)の canonical economic model を GUI に落とす設計。main agent(Opus 4.8)案 → Codex(gpt-5.5)共同レビュー。

## 1. 現状の問題 (確定)

### 1.1 金額が7箇所に散在(基準バラバラ)
1商品の expander 内に金額が分散し、それぞれ基準(商品のみ/総額/利益/還付有無)が違う:

| 場所 | 金額 | 基準 |
|---|---|---|
| Hero: 現在総額 | $798 | 総額(商品+送料) |
| Hero: 損益分岐 | $601 | 商品のみ |
| Hero: 現在粗利 | $+89 | 商品のみ差 |
| Hero: 競合最安 | $815 | 総額 |
| W147: 還付あり×DDP/DDU | ¥16,871 / ¥21,135 | 利益(還付込) |
| W147: 還付なし×DDP/DDU | ¥10,962 / ¥15,226 | 利益(還付抜) |
| 💰仕入価格+下限 | ¥65,000 / $- | 原価 / 商品のみ |
| 🏪仕入先候補 | ¥… | 原価候補 |

→ **総額($798)と商品のみ($601)が隣接して誤読を誘発**(本件の発端)。

### 1.2 1 expander に16セクション縦積み = ごちゃつき + 低速
Hero / 利益サマリ / 🏷️SKU / 📦物理属性 / 🌐区分 / 💵eBay出品 / 💰仕入+下限 / 📎メモ / 🔗URL投入 / 📊仕入先状態 / 🔧仕入先URL / 監視URL / 🏪仕入先候補 / 🎯ライバル / CLI検索結果 / 値下げ履歴。
- 縦スクロール膨大、関連情報が分断
- Streamlit は widget 操作毎に全再描画 = 商品数×16セクションの widget で重い

## 2. 設計原則 (100点の定義)

### 原則A: 金額は「2つの視点」だけに正規化する
ごちゃつきの根因は buyer視点 と seller視点 の混在。**全金額をどちらか一方に明示帰属**させる:

- **buyer視点(eBayでの見え方 / 競争軸)**: 買い手総額 = 商品価格 + 送料。競合最安と戦う軸。
- **seller視点(あなたの取り分)**: 実利益 = 売上 − 原価 − eBay手数料 − 物流費 − 実関税。損益分岐・下限もここ。

→ **損益分岐は競合と比べる時は「総額軸」で出す**(現在総額・競合最安と同じ物差し)。誤読が物理的に消える。

### 原則B: canonical economic model 1本から全表示を導出 (W212連動)
W212 の単一モデル(item_price_usd / buyer_shipping_usd / actual_duty_cost_jpy / shipping_cost_jpy / fee_base / profit_ex_refund / profit_with_refund / market_pattern / duty_source_confidence)を1回計算し、UI は全部そこから読む。**呼び出し元依存の金額定義を撤廃**。

### 原則C: 一覧は1行密度、詳細はタブ(16→4)
- **一覧 = 1商品1行**: 買い手総額 / 実利益率 / 競合差 / 在庫 の4数値を色付きで scannable に
- **展開 = 4タブ**: 💰採算 / 📦出品 / 🏪仕入 / 🎯競合(16セクションを4束に)

### 原則D: サクサク (Streamlit 高速化)
- `st.fragment`(部分再描画)で1商品カードの操作が全ページ rerun を起こさない
- 経済計算は `@st.cache_data`(db_version + settings_mtime key)で1回
- 一覧は最小 widget、詳細は展開した1件のみ render(他は折りたたみ)
- breakeven を rerun 毎再計算しない(W156 の二重計上 fix 流儀で cache)
- ページネーション維持

改善点:
- 金額が **buyer列 / seller列** の2列に正規化(散在解消)
- **損益分岐を総額軸 $709 で表示** → 競合最安 $815・買い手総額 $798 と直接比較可(現状の $601 商品のみ誤読を根絶)
- **実関税を明示**(HS + 確信度)= washing 修正(W212)を可視化。Section232該当時の警告
- **実利益 と 手取り(還付込)を上下で分離**(基準明示)
- 採算が1タブに集約

## 7. Codex(gpt-5.5)共同レビュー結果 → 最終統合 (2026-06-02)

main agent 案と強く収束。Codex の重要追加3点 + 段階導入順序を採用。

### 追加A【最重要・金銭直結】損益分岐は「二重 floor」で管理 (確信度 HIGH)
UI で損益分岐を総額軸 $709 で見せるのは良いが、**自動値下げ(W183)が内部で使う floor は商品価格軸**(task_rival_pricing.py:443 `lp_min_price>0 ? lp_min_price : lp_breakeven_usd`、520 で競合総額−自社送料=StartPrice)。**総額値を `lp_min_price` に保存したら W183 が壊れる**。モデル/DB は必ず2値:

| フィールド | 用途 |
|---|---|
| `breakeven_item_price_usd` | **W183/ReviseFixedPriceItem 用の唯一の floor**(商品価格軸、保存値) |
| `buyer_shipping_usd_at_floor` | その floor 算出時の送料/関税徴収額 |
| `breakeven_buyer_total_usd` (= 上2つの和) | **UI表示専用**(総額軸、保存しない) |
| `floor_basis_version` | duty_pattern / primary_market / 送料取得元 / settings hash |

→ UI 編集欄と保存値は「自動値下げ下限(商品価格) $601」と明示、表示は「損益分岐(総額) $709」。**総額値を floor に保存させないのが絶対条件**。

### 追加B 一覧行は4数値 + 警告バッジ1種 (確信度 中高)
数値を増やすより事故条件をバッジ化(密度を壊さない): `未FIX / 関税低確信 / floor未設定 / 還付込みのみ黒字 / Section232注意`。既存フィルタ(未FIX/競合0/在庫切れ/利益マイナス、tab_product_management.py:357)を活かす。

### 追加C Streamlit 高速化 強化 (確信度 HIGH)
- **expander 廃止 → `st.dataframe`/HTML table + 選択中1件だけ詳細 render**(最大の高速化)
- 詳細計算も選択中 ItemID のみ実行
- canonical model を **DB materialized cache** 化(一覧では再計算しない)
- 競合/仕入先/CLI検索結果は**タブを開いた時だけ lazy load**
- `st.fragment` は「1商品詳細」「競合追加」「仕入候補採用」単位に限定

### 微修正(タブ): 価格・下限編集は採算タブ、ただし eBay反映ボタンは出品タブにもミラー(意思決定と実行の分離)

### 段階導入順序(両者合意・壊さず移行)
1. **calculator で washing 分離**(`buyer_shipping_usd` と `actual_duty_cost_jpy` を別項目) ← W212 最優先・前提
2. **canonical economic model DTO 追加**(既存UIは変えず計算結果だけ)
3. **hero だけ canonical panel に差替**(16セクションは下に残す、まず金額誤読を止める)
4. **W183 floor を軸明示**(`lp_breakeven_usd` は商品価格軸維持、UIだけ総額換算併記)
5. **一覧行を4数値+警告バッジ**(既存フィルタ/ページネーション維持)
6. **16セクション→4タブ**(関数は壊さず配置だけ、最後に重い仕入先/競合/CLI を lazy render)

### 設計案の訂正(Codex指摘、md-files-can-be-wrong)
§3 表で `mixed_global` の washed を「自然な正解」のように見せている → 真のバグは breakeven ズレでなく **washing 自体**(合意文書 §7)。本パネルは washing 修正後の実関税を表示する前提。
