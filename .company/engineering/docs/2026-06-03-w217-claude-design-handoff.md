## 2. ⚠️ 最重要: なぜ現状が乖離したか (技術的制約 — 設計の前提)

このツールは **Streamlit** (Python の Web アプリフレームワーク) で作られている。Streamlit には以下の構造的制約があり、**素の Streamlit ウィジェットでは モックの見た目を再現できない**:

- **`st.markdown('<div>...')` は後続のウィジェットを囲めない**: HTML の `<div>` 枠で入力欄を囲もうとしても、div が即閉じてウィジェットは枠の外に出る。→ モックの「💰金額枠 (amber 左ライン囲み)」が作れず、現状は「見出しの色」で代替してしまった。
- **入力ウィジェット (`st.number_input` / `st.selectbox`) は見た目が固定**: ラベルが上付き・高さが大きい・数値に +/- ステッパーが付く等。モックの「コンパクトな枠内インライン入力」にはできない。
- **左ナビは `st.sidebar`**: 横幅を食う。上部移動は可能だが Streamlit 標準にはない (カスタム HTML/CSS or `streamlit-option-menu` 等が要る)。

### 結論 (デザイン方針の分岐)
- **表示部分 (採算パネル / ライバル表 / バッジ / 競合差 / 警告)** は `st.markdown(unsafe_allow_html=True)` で **純 HTML として描画でき、モックとほぼ同一にできる** (採算パネルは既にこの方式)。
- **入力部分 (価格 / 送料 / 区分 / 仕入 / 寸法 等)** は Streamlit ウィジェットで、**CSS 注入で近づけられるが pixel-perfect は不可**。完全一致が必須なら **カスタムコンポーネント (React/HTML+JS) 化** が必要。

→ Claude Design への問い: 「(A) 表示は HTML 完全一致 + 入力は CSS で最大限寄せる現実解」か、「(B) カスタムコンポーネントで pixel-perfect」か、どちらの方針で詰めるか。

## 4. 絶対に壊してはいけない機能ロジック (money-direct / 過去に事故)

デザインを変えても、以下の **動作** は維持必須 (見た目だけ変える):

1. **競合データの全置換と再シード**: フォーム保存時に競合を全置換する。編集グリッドのウィジェットが正しく seed されないと **登録済み競合が全消失** する事故が過去にあった (現実装は折りたたみでも安全を実機確認済み)。配置を変える時はこの seed 機構を壊さない。
2. **送料/BP の dirty-flag**: 編集していない送料を誤って eBay に巻き戻すと **DDP 関税 buffer 喪失 = 赤字**。初期値 capture と submit の参照関係を壊さない。
3. **SKU は商品識別キーにしない** (在庫種別 prefix と仕入先URL変換の 2 用途のみ)。識別は `ebay_item_id`。

→ Claude Design は **見た目 (HTML/CSS/配置)** を設計し、**Python の保存ロジックは触らない** 前提。
