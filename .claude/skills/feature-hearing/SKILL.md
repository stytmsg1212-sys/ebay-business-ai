# Feature Hearing Skill — 暗黙知を吸い上げてシステム化する

新機能・自動化を作る前に、**オーナーの業務判断ロジック(暗黙知)を CDM ヒアリングで言語化**し、それを設計の元仕様にするための skill。「コードを書く前に、専門家の頭の中を吸い上げる」。

## いつ発火するか

- user が「**○○機能を追加したい / ○○を自動化したい / ○○を相談したい**」と発話
- user が「ヒアリングして」「私のノウハウを引き出して」と明示
- assistant が「これは user 固有の業務判断が核心の大型機能 = まず暗黙知抽出すべき」と判断（その場合は user に「ヒアリングから始めてよいか」確認）

## 大原則（厳守）

1. **ヒアリングに徹する。性急にまとめ・実装に走らない。** 一度に一つだけ深掘りする。
2. **抽象ルールを聞かない。具体ケースを聞く**（CDM）。「あなたのルールは?」でなく「直近で○○と判断した具体例を1つ思い出して。何を見て決めた?」。
3. user の脱線は歓迎（脱線に本音=暗黙知が出る）。

## 手法（学習済の研究ベース技法）

- **Critical Decision Method (CDM)** (Klein/Crandall/Hoffman 1998): 具体的な過去の1ケースを再生 → cue(何を見たか)と判断を probe で掘る。
- **Thinking Aloud**: 可能なら実データ(実画面/実レコード)を見せて判断を実況させる。一覧/スクショ/DBの実物を出す。
- **backtracking**(清水久三子『聞き方の教科書』): 相手の答えを言い換えて確認し、ズレを直しながら更に掘る。
- **funnel / 仮説力**(野口吉昭『質問力』): 固まってきたら**仮説をぶつけて確認**（「つまり○○という1本のルールですね?」）。当たれば背骨が固まり、外れれば訂正で更に精度が上がる。

## 進め方（7ステップ）

1. **既存システムを先に把握**（K0）: 関連コード/KB/memory を grep・Explore で確認。「もう実装済」を二重に作らない。`vero_brands.json` の様に **md記述と実体が乖離**していることもあるので実物確認(md-files-can-be-wrong)。
2. **CDM ヒアリング**: 上記手法で一問一答。ライフサイクル等の軸で「順番に」進めると漏れにくい(例: 発見→仕入→値付け→撤退)。各回 = backtrack確認 + 1 probe。
3. **データ実現性を都度検証**: 「その判断に使う信号は取れるか」を実際にテスト（例: GetItem で競合ソールド数が取れるか実証）。「APIで取れない」は1手段の話、負の能力主張ゲートで他手段を試す。
4. **詳細議事録を作成**: `.company/engineering/docs/YYYY-MM-DD-<topic>-hearing-minutes.md`（Obsidian の company ジャンクションで user が閲覧/添削可）。user の言葉と assistant 補足を区別。確定/未決/論点を明記。
5. **外部AIで漏れチェック**: `codex-reviewer`(+必要なら `fugu-reviewer`)に議事録を渡し「論理矛盾/抜け/危険な単純化/次に聞くべき暗黙知」を出させ、2段ループで再評価。
6. **メモリに永続化**: 議事録への pointer を memory に置き `MEMORY.md` 索引へ。Obsidian 連携(`obsidian-vault/memory` ジャンクション)で user の添削が AI の頭脳に蓄積される。
7. **システム化へ橋渡し**: 議事録を元仕様に `code-architect` で設計 → `code-reviewer`+Codex 2段 → 実装(Q1検証)。money-direct は採用と自動実行の分離 + Shadowモード + 提案止まりを既定に。

## 出力物

- 詳細議事録(`.company/engineering/docs/`)
- Codex 漏れチェック結果
- memory pointer + `MEMORY.md` 索引行
